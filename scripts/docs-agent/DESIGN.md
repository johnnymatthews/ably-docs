# Docs Agent: implementation plan

Companion to "Automagic docs". That doc says what and why. This one says how, in enough detail to build a demo in the `ably-docs` fork and to answer "but how would that actually work?" in the session.

Status: draft, 24 Nov 2026. Nothing here has been run yet. Items marked **(confirm)** depend on files I couldn't read.

## 1. The one-slide version

```
Product repo                          Docs repo (fork for the demo)
------------                          -----------------------------
Feature PR
  + label `needs:docs`  ──trigger──▶  1. Collect context (diff, PR text, existing docs)
                                      2. Draft docs (agent, no write access)
                                      3. Verify (plain scripts, not the model)
                                      4. Publish (separate job: draft docs PR)
Comment on feature PR  ◀───────────   5. One short comment, links the draft PR
Engineer: 👍 / reply / ignore
                                      6. Docs Engineering reviews and merges
```

Four ideas carry the whole design:

- **Generate what can be generated.** If a page can be derived mechanically from a source of truth in an engineering repo (error codes, an OpenAPI spec, a release version), a script produces it and the agent never writes it. The agent only drafts what no source can produce: guides, concepts, how-tos, feature pages. See the routing rule below.
- **The model never holds write access.** One job drafts. A different job, with only the permissions it needs, publishes.
- **Verification is plain code, not the model grading itself.** Every identifier in the draft has to be found in the PR or the existing docs, or it goes on the "not sure" list.
- **Nothing merges without a person.**

### Routing rule: generate where a source of truth exists, draft where it doesn't

Ably already works this way for error codes, and I'd make it the general principle. A page is either **generated** (derived from a source, never hand-edited) or **drafted** (written by the agent, reviewed by a person). Every page the bot touches gets sorted into one of those two lanes.

What the fork shows today:

| Kind of page | Example in the fork | Source of truth | Status |
|---|---|---|---|
| Error code pages | `src/pages/docs/platform/errors/codes/*`, about 277 of the 788 MDX files, each stamped `AUTOGENERATED — DO NOT EDIT` | `ably-common/errors/codes/*.md` | **Generated already.** CI regenerates and fails on any diff. |
| REST API reference | `api/control-api`, `api/chat-rest`, `api/liveobjects-rest`, rendered by Redoc | OpenAPI files in `static/open-specs/` (`control-v1.yaml`, `chat.yaml`, `liveobjects.yaml`) | **Rendered from a spec already.** The specs are committed in the docs repo. I haven't seen how they're kept in sync with the engineering repos. **(confirm)** |
| SDK API reference | `api/realtime-sdk/*.mdx`, `api/rest-sdk/*.mdx` | SDK source and docstrings, across many languages | **Hand-written MDX today** (no generated marker). A candidate for generation, but the many languages make that a larger job. Treat as a hypothesis. |
| Version and language tables | `src/data/languages/languageData.ts` | SDK releases | `CONTRIBUTING.md` describes it as bumped when a release ships. Whether that's automated is unknown. **(confirm)** |
| Guides, concepts, how-tos, feature pages | `chat/rooms/*`, `ai-transport/*`, getting started | None. These carry intent, the "why", and the reader's journey | **Drafted** by the agent, reviewed by a person. |

How the routing works:

1. **Classify.** For each page the PR affects, ask whether it has a generated representation: did the PR change a spec file, a registry entry, or a public signature?
2. **Generated lane.** The agent writes no prose. It checks that the *source* was updated, then runs the generator so the regenerated pages are part of the draft PR. The most useful thing the bot can do here is catch a stale source. Example comment: "This PR adds error code 4xxxx but there's no registry entry, so no error page will exist."
3. **Drafted lane.** Everything else goes to the agent, with the limits in sections 4 to 6.
4. **Link, don't restate.** A guide that needs a fact owned by a generated page (an error's meaning, an option's default, an endpoint's parameters) links to that page instead of copying the text. Copies are how guides drift from reference.
5. **One draft PR, two labelled lanes.** The PR body marks each changed file `generated` or `drafted`, so reviewers know which files need a skim ("does the generator output look sane?") and which need a real read.

**Where there's no source of truth yet.** Where an API has stable endpoints and no spec, adding an OpenAPI file (ideally generated from the code, so there's still one source and not two) is a better investment than having an agent write reference prose. That's an option to raise with the owning team, not something the bot does itself. It adds an artifact someone has to maintain.

**What the generator guard looks like.** Copy the existing pattern: a CI job runs the generator and fails if the committed output differs. The verifier also rejects any agent edit to a file carrying the `AUTOGENERATED` marker (section 6, check 3).

## 3. Components

| # | Component | Runs in | Permissions | Job |
|---|---|---|---|---|
| 1 | Trigger | Product repo | Dispatch to docs repo only | Fires when a person adds `needs:docs` |
| 2 | Context builder | Docs repo, job `draft` | Read only | Gathers the PR diff, PR text, linked issue, and existing pages that mention the same names |
| 2b | Router and generators | Docs repo, job `draft` | Read only | Sorts each affected page into the generated or drafted lane, runs the existing generators (`yarn generate:errors`, and any spec sync), and flags stale sources |
| 3 | Drafter | Docs repo, job `draft` | Model key, no GitHub write token | Produces a structured draft (section 5) for the drafted lane only |
| 4 | Verifier | Docs repo, job `draft` | Read only | Plain scripts check the draft (section 6) |
| 5 | Publisher | Docs repo, job `publish` | Contents + PRs write | Applies allow-listed file changes, opens the draft PR |
| 6 | Commenter | Docs repo, job `publish` | PRs write on the product PR | Posts or updates the one comment |
| 7 | Reply handler | Docs repo | Same as publisher | Revises the draft once on engineer correction |
| 8 | Reaction poller | Docs repo, scheduled | Read only | Records 👍 reactions (section 8) |
| 9 | Run log | Docs repo | n/a | One JSON line per run, feeds the success measures |

**Pipeline-agnostic core.** Components 2 to 5 are plain Node scripts under `scripts/docs-agent/`, called as `node scripts/docs-agent/<step>.mjs`. GitHub Actions is a thin wrapper that calls them in order. If Ably moves it to CircleCI or anything else, only the wrapper changes. This answers "which CI/CD system?" without needing to know.

## 4. The workflow, step by step

1. **Label.** An engineer with write access adds `needs:docs` to a feature PR. Only people with write access can add labels, which is the gate, and the trigger workflow also checks org membership the way `review-app.yml` does. The label is also the opt-in: no label, no run.
2. **Trigger.** A small workflow in the product repo sends a `repository_dispatch` to the docs repo with the PR URL. It sends the URL and nothing else, and the docs side fetches everything itself.
3. **Collect context** (job `draft`).
   - PR title, description, labels, linked issue, changed file list, diff (capped in size, with a note if truncated).
   - Existing docs: search the docs repo for the public symbols and option names found in the diff, and pull the matching pages and nav entries.
   - House rules: `CLAUDE.md`, `writing-style-guide.md` and the `write-docs` skill (its page-type templates and verification checks).
   - **Route.** Sort each affected page into the generated or drafted lane (see the routing rule in section 1). Run the generators for the generated lane and record any stale source.
4. **Draft.** The agent writes only the drafted lane. It returns the JSON in section 5: file edits, a two-sentence summary, and a list of things it isn't sure about. It may only propose changes under allow-listed paths (docs content and nav under `src/pages/docs` and `src/data/nav`), and never to a file marked `AUTOGENERATED`.
5. **Verify.** Scripts in section 6 run. Failures don't block the draft. They move claims onto the "not sure" list and set `needs_human_attention: true` on the run log.
6. **Publish** (job `publish`, a separate job). It downloads the draft as an artifact, treats it as untrusted data, re-checks the paths against the allow-list, creates a branch `docs-agent/<repo>-<pr-number>`, commits, and opens a **draft** PR requesting `@team-deved`. The PR body follows the template in section 7.
7. **Comment.** One comment on the feature PR, using the template in section 7. If a run happens again for the same PR, the comment is edited in place rather than a second one being added.
8. **Engineer response.** Ignore, 👍, or correct. See section 8 for what the system can actually detect.
9. **Human review.** Docs Engineering reviews the draft PR with the verify results on the page. If the engineer stayed silent or disagrees, Docs Engineering resolves it, and falls back to the Engineering PM if needed (as in the original doc).
10. **Merge** is manual, always.

## 5. The draft: output contract

The agent has to return JSON in this shape, which the verifier and publisher both read:

```json
{
  "summary": "Two sentences: what users can now do, and why it matters.",
  "feature_version": "x.y.z",
  "edits": [
    { "path": "src/pages/docs/...", "action": "modify|create", "content": "..." }
  ],
  "nav_changes": [ { "path": "src/data/nav/...", "patch": "..." } ],
  "claims": [
    { "text": "setX() takes a number of milliseconds", "evidence": "file:line or docs path" }
  ],
  "not_sure": [ "Whether the default is per-channel or global" ]
}
```

The `claims` list is what makes verification possible: the agent has to point at where each factual claim comes from. A claim with no evidence goes straight to `not_sure`.

## 6. Verification: plain scripts, not the model

Each of these is deterministic and fast:

1. **Symbols exist.** Every inline-code identifier and every identifier inside a code block must appear in the PR diff, the repo at the PR's head commit, or the existing docs. A miss is flagged. This catches invented methods, which is the failure that does the most damage.
2. **Evidence resolves.** Every `evidence` pointer exists and contains the claimed text.
3. **Allow-listed paths only, and generated files are off limits.** Edits outside the content and nav directories are dropped. Any edit to a file carrying the `AUTOGENERATED — DO NOT EDIT` marker is rejected, because only the generator may change it.
4. **Build passes.** Run the repo's existing build and lint steps on the branch. The per-PR review site already does a build, so this adds little.
5. **Style rules.** Version admonition present for new or changed features. Nav entry exists for any created page. Run the mechanical checks from the `write-docs` skill (it lists binary, agent-checkable rules, such as no em dashes, a hook in the opening, and no API keys in client code), and `yarn lint`.
6. **Code samples.** Where the sample is runnable and the SDK is available, run it against a throwaway app **(stretch goal, skip for the demo)**.

Every run records how many claims were checked, how many failed, and how many moved to `not_sure`. That's the "factual errors per draft" measure in the original doc.

## 7. What people see

**Comment on the feature PR** (about 60 words, casual, one per PR, hidden marker for idempotency):

```markdown
<!-- docs-agent:v1 -->
Hi, I'm the Docs Agent. I read this PR and think it lets users {X}, so that {Y}.
I've drafted docs here: {draft PR link} (preview: {review site link}).
I'm not sure about: {Z}.

If that's right, 👍 this comment. If I've got it wrong, reply starting with `docs:` and I'll revise once.
Ignore this and Docs Engineering will pick it up.
```

**Draft docs PR body:**

```markdown
Source PR: {link}
Drafted by the Docs Agent. A person must review before merge.

**Summary:** {two sentences}
**Files changed:** {list}
**Not sure about:** {list from not_sure}
**Verification:** {n} claims checked, {n} failed, {n} moved to not-sure
**Engineer response:** none yet
```

Labels on the draft PR: `docs-agent`, plus `needs-human-attention` when the verifier flagged anything.

## 8. Engineer responses: what's actually detectable

The original doc has the engineer reply with an emoji. That needs care, because it doesn't map neatly onto GitHub:

- **Reactions don't fire any event.** GitHub doesn't send a webhook when someone reacts to a comment, so a workflow can't wake up on a 👍. The only way to see it is to read the reactions through the API. So component 8 is a scheduled job (say hourly while a draft is open) that reads reactions on the bot comment and writes `Engineer response: 👍` into the draft PR body and the run log. Docs reviewers also just see the emoji on the thread, so nothing breaks if the poller is late.
- **Comments do fire an event** (`issue_comment`), but that event fires for every comment on the PR, not just replies to the bot. PR conversation comments aren't threaded. To avoid revising on chatter, the reply handler only acts when the comment is from the PR author or a member, starts with `docs:` (or mentions the bot), and the run log shows zero revisions so far. That's a small change from "just reply" and worth a decision from you.
- **The bot's own comments won't trigger anything.** Comments posted with the built-in workflow token don't start new workflow runs. That's a feature here (no loops), but it means the revise step can't be chained off its own output.

**Revise once** means: the reply handler re-runs the drafter with the original context plus the correction text (treated as untrusted input like everything else), pushes to the same branch, edits the comment in place, and sets `revisions: 1`. A second correction is left for a human.

## 9. Security model

This section replaces the "no secrets" line in the original doc, which isn't quite true: the agent needs a model API key, and publishing needs a token.

| Risk | Control |
|---|---|
| Someone runs the bot on a PR they shouldn't | Label-gated. Only people with write access can add it. No label, no run. |
| Prompt injection in PR text, diff, comments or branch names | All PR-derived text is wrapped as data in the prompt and never treated as instructions. The drafter has no tool that can write, and no GitHub token. Its only output is JSON that the next job validates. |
| Shell injection through PR titles or branch names | Never interpolate `${{ github.event... }}` into `run:` steps. Pass every PR-derived value through `env:` and read it in code. |
| Secret exposure | Model key exists only in job `draft`. GitHub write token exists only in job `publish`. Neither job runs code from the PR. |
| "Pwn request" pattern | The workflow never checks out and runs code from the product PR. It reads the PR through the API. If it needs the repo at the PR's head commit for symbol checks, it reads files, never runs them. Avoid `pull_request_target`. |
| Runaway cost | Spend cap on the model key, cap on diff size, one run per label event, one revision per PR. |
| Wrong content published | Draft PR only, human review, no merge permission anywhere. |
| Supply chain | Pin third-party actions to commit SHAs. |

Cross-repo trigger: the product repo needs a token that can dispatch to the docs repo. Use a fine-grained token or GitHub App scoped to that single permission. A label added on a PR from an external fork won't have access to secrets, so for Ably's own engineers (who push branches in the repo) it works, and external contributor PRs would be picked up by a docs person re-adding the label.

## 10. Workflow sketch (untested)

Docs repo, `.github/workflows/docs-agent.yml`:

```yaml
name: docs-agent
on:
  repository_dispatch:
    types: [docs-agent-run]
  workflow_dispatch:            # used for the replay demo
    inputs:
      source_pr:
        description: URL of the feature PR to replay
        required: true

permissions: {}                 # nothing by default; each job asks for what it needs

jobs:
  draft:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    env:
      SOURCE_PR: ${{ github.event.client_payload.pr || inputs.source_pr }}
    steps:
      - uses: actions/checkout@<pinned-sha>
      - run: node scripts/docs-agent/collect.mjs "$SOURCE_PR" > context.json
        env:
          GH_TOKEN: ${{ github.token }}
      - run: node scripts/docs-agent/route.mjs context.json > routed.json   # sorts pages into generated/drafted lanes, runs generators
      - run: node scripts/docs-agent/draft.mjs routed.json > draft.json     # agent sees only the drafted lane
        env:
          MODEL_API_KEY: ${{ secrets.DOCS_AGENT_MODEL_KEY }}
      - run: node scripts/docs-agent/verify.mjs draft.json routed.json > verified.json
      - uses: actions/upload-artifact@<pinned-sha>
        with: { name: draft, path: verified.json }

  publish:
    needs: draft
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
    env:
      SOURCE_PR: ${{ github.event.client_payload.pr || inputs.source_pr }}
    steps:
      - uses: actions/checkout@<pinned-sha>
      - uses: actions/download-artifact@<pinned-sha>
        with: { name: draft }
      - run: node scripts/docs-agent/publish.mjs verified.json "$SOURCE_PR"
        env:
          GH_TOKEN: ${{ github.token }}
```

Product repo trigger (thin):

```yaml
name: request-docs
on:
  pull_request:
    types: [labeled]
jobs:
  dispatch:
    if: github.event.label.name == 'needs:docs'
    runs-on: ubuntu-latest
    steps:
      - run: gh api repos/ably/docs/dispatches -f event_type=docs-agent-run -f "client_payload[pr]=$PR_URL"
        env:
          PR_URL: ${{ github.event.pull_request.html_url }}
          GH_TOKEN: ${{ secrets.DOCS_DISPATCH_TOKEN }}
```

Fork settings to enable before it works: Actions turned on for the fork, and "Allow GitHub Actions to create and approve pull requests" under Settings, Actions, General. Forks have workflows disabled by default.

## 11. Run log and measures

One line per run, appended to a log file on a `docs-agent-log` branch (or kept as a workflow artifact for the demo):

```json
{ "source_pr": "...", "draft_pr": "...", "started": "...", "label_to_draft_seconds": 0,
  "claims_checked": 0, "claims_failed": 0, "not_sure": 0,
  "engineer_response": "none|thumbs_up|correction", "revisions": 0,
  "merged": false, "lines_changed_by_reviewer": 0 }
```

How each measure from the original doc gets fed:

| Measure | Source |
|---|---|
| Share of drafts merged, how heavily edited | `merged`, `lines_changed_by_reviewer` (diff between the bot's commit and the merge commit) |
| Engineer responses | `engineer_response`, filled by the poller and the reply handler |
| Time from feature PR to merged docs PR | Timestamps on both PRs |
| Factual errors found per draft | `claims_failed` from the verifier, plus errors reviewers log when they edit |
| Agents answering better | Not in this pipeline. It comes from the separate agent test (A/B/C conditions) |

## 12. The replay demo

You can't add a label in Ably's repos, so the demo replays a real PR through `workflow_dispatch`.

**Picking the PR.** Look for a merged PR in a public Ably SDK repo (ably-js, ably-chat-js, and so on) that adds a user-facing feature or option, touches fewer than about 10 files, has a decent PR description, and shipped in a release. Ideally the live docs on ably.com/docs (the `.md` version of a page is a handy way to read them) already document it, because then you can compare the bot's draft with what Ably wrote.

**Running it.**
1. Run the workflow with the PR URL.
2. Open the draft PR it creates and the comment it would have posted (for the demo, post it into the fork's own PR, since you can't comment on Ably's).
3. Fill in the results table in the original doc: what matched, what the bot got wrong, what you changed.
4. Keep the transcript. It feeds the "how I used AI" section.

**What counts as success.** Nothing needs to be perfect. A draft that's 70% right with its uncertainty flagged honestly is a better demo than a flawless one, because it shows the verify step doing real work. If the bot invents something and the verifier catches it, say so in the session.

**Caveat to state up front.** The archived repo is older than the live docs, so the draft lands in an older structure. Say it before anyone asks.

**Time budget.** The presentation plan gives the bot one slide. If time is short, the section 1 diagram plus the replay result is enough, and everything else here is back-pocket for questions.

## 13. Questions to put to Ably

These are in the original doc, with sharper framing:

1. What does the existing generation system (the one behind the error pages) take as input, and does it run on feature PRs or only on registry changes? I'd be extending it, not replacing it.

6. How do the OpenAPI specs in `static/open-specs/` get from the engineering repos into the docs repo today: by hand, or by a sync? If by hand, a sync job with a drift check (the error-page pattern) is the first deterministic win.
7. Are the SDK reference pages (`api/realtime-sdk`, `api/rest-sdk`) written by hand, or derived from SDK docstrings somewhere I can't see? That decides whether they sit in the generated or drafted lane.

## 14. Changes I'd make to the original doc before presenting

- **"It has no secrets and minimal permissions"** isn't accurate as written. Say "the drafting step has no GitHub write access, and the publishing step never sees the model key". Section 9 has the detail.
- **Emoji reply.** Say that reactions are read on a schedule rather than triggering a run, or someone at Ably will point it out.
- **"Engineers don't like writing or reviewing docs"** (assumption 3) sits badly with your plan to soften "engineers shouldn't own docs". Something like "engineers would rather spend their time confirming intent than writing prose" makes the same point without the dig.
- **The docs-driven-development line** ("I don't wanna ruffle any feathers") is charming but reads as a dig at their current process. Consider cutting it.
- **Numbered sub-steps.** The `a. a. a.` items under step 2 won't render as a list in most markdown. Use `-` or indent properly.
- **Typos:** "wrinting", "y following", "Engieering", "get's", "repond", "Enginerring", "engieering", "sever-side" (in the other chat's copy).
